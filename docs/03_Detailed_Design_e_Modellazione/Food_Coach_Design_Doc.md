## Problem Statement

Lo spreco alimentare domestico è un problema enorme (75kg/anno a famiglia in Italia), ma le app esistenti lo affrontano nel modo sbagliato:

- Sono **reattive** — aspettano che tu abbia avanzi e ti dicono cosa cucinare
- Richiedono **troppo effort** — importare ricette, scansire manualmente, correggere ingredienti
- Danno **ricette AI scadenti** — gli LLM generici producono risultati "strani" e non contestualizzati
- Non **cambiano il comportamento** a lungo termine — l'utente resta dipendente dall'app
- Sono **single-user** — ignorano il contesto famiglia/gruppo

L'utente target (famiglie, studenti, lavoratori) non spreca cibo per cattiva volontà, ma per **mancanza di organizzazione, educazione e guida**. Saper fare la spesa in modo intelligente, conservare gli alimenti correttamente e cucinare sfruttando gli avanzi sono **competenze che si imparano** — e nessuna app oggi le insegna.

## What Makes This Cool

Food Coach non è un'app di ricette. È un **alleato che ti rende autonomo**.

La filosofia è **anti-Tinder**: mentre Tinder guadagna se rimani single, Food Coach ha successo quando l'utente **non ha più bisogno dell'app** perché ha interiorizzato le competenze. Questo crea un rapporto di fiducia radicalmente diverso: l'app è onesta, educa, e si impegna a migliorare l'utente davvero.

**Cosa la rende unica:**

1. **Educazione progressiva** — non solo "cosa cucinare", ma "come pensare al cibo". Ogni interazione è un micro-insegnamento
2. **Pianificazione proattiva** — evita lo spreco a monte (pianificazione settimanale + lista spesa ottimizzata) invece di rincorrere gli avanzi
3. **RAG pipeline specializzata** — Retrieval-Augmented Generation su ricette strutturate + LLM refinement, non un generico ChatGPT
4. **Multi-utente** — pensata per famiglie e convivenze, non per l'individuo
5. **Budget-first** — l'€ risparmiato è l'hook principale (più efficace dell'appello ambientalista)

## Premises

1. **Le persone sprecono per mancanza di competenze, non di strumenti.** Un'app che insegna a pianificare, conservare e cucinare è più efficace di una che solo "traccia".
2. **Il risparmio economico è l'hook più forte.** Mostrare € risparmiati è più motivante di kg di CO2 o buoni propositi ecologici.
3. **L'educazione progressiva fidelizza più dei punti gamification.** Se l'utente migliora davvero, diventa ambassador del prodotto.
4. **RAG batte LLM generico per suggerimenti ricette.** Retrieval-Augmented Generation (retrieval strutturato + LLM refinement vincolato) produce risultati migliori di "chiedi a GPT cosa cucinare".
5. **Multi-utente è un differenziatore reale.** Nessuna app leader supporta la pianificazione familiare condivisa.

## Approaches Considered

### Approach A: Reactive Recipe App (what everyone does)
Scansione ingredienti → ricette AI. Il modello standard. Basso effort iniziale ma nessun cambiamento comportamentale.

### Approach B: Food Dashboard & Tracker
Tracciamento della spesa + € sprecati + CO2. Bello per data viz ma non aiuta attivamente l'utente a sprecare meno.

### Approach C: Food Coach (scelto)
Educazione proattiva + pianificazione + ricette con RAG pipeline + impatto. Copre l'intero ciclo: pianifica → compra → conserva → cucina → impara.

## Recommended Approach

**Food Coach (Approach C)** perché:
- Attacca la causa, non il sintomo
- È differenziante rispetto a Remy, OH a potato!, Cucinalo, Avanzō, FreshMind
- La filosofia anti-Tinder crea un posizionamento di marca forte e autentico
- Copre l'intero ciclo, massimizzando il valore per l'utente
- Offre il miglior percorso di apprendimento per Alin (full-stack + RAG + UX)
- **Decisione architetturale:** Si inizia con backend Python (web app) — React Native arriva dopo che il recommendation engine è validato. Riduce la complessità iniziale e permette di concentrare l'apprendimento su uno stack alla volta

### Pipeline AI: RAG (NO fine-tuning)

**Chiarezza: questa NON è una pipeline di fine-tuning.** Non alleniamo nessun modello. Usiamo **RAG (Retrieval-Augmented Generation)**:

```
Input ingredienti → [1] Embedding search → [2] LLM refinement (cloud API)
```

| Cosa NON è | Cosa È |
|---|---|
| ❌ Fine-tuning di un modello su ricette italiane | ✅ Retrieval da DB strutturato |
| ❌ Modello self-hosted sul telefono dell'utente | ✅ LLM in cloud (Gemini API), chiamato dal backend |
| ❌ Training custom costoso | ✅ Embedding pre-trained + prompt engineering |

**Dove gira cosa:**
- **Embedding search** → server (Python su Railway o VPS). Il modello sentence-transformers è leggero (CPU)
- **LLM refinement** → **cloud API** (Gemini free tier). Niente modelli sul telefono dell'utente. Il backend Node.js chiama l'API e il telefono riceve solo il risultato finale
- **Self-hosting futuro** (se i costi crescono) → su server, non su dispositivo mobile

**Perché RAG risolve il problema delle "ricette strane":**
1. **L'embedding search recupera ricette reali** da un dataset strutturato — non inventa nulla. Se il DB ha "Pasta al Pomodoro", quella è la base
2. **Il LLM non genera da zero**: riceve le top-10 ricette e le raffina (adatta quantità, unisce suggerimenti, spiega perché funzionano)
3. Il retrieval agisce come **grounding context** che riduce le allucinazioni
4. L'utente vede ricette con sourcing trasparente

Esempio prompt template per il refinement:
```
Hai a disposizione queste ricette reali dal nostro database: [TOP-10 retrieved].
L'utente ha questi ingredienti: [input].
Scegli le 3 migliori e adattale. Spiega perché funzionano con gli ingredienti disponibili.
```

### Fallback creativo (casi limite)

Quando le ricette nel DB non coprono gli ingredienti dell'utente (es. "wrustel, pasta, noci"), il sistema ha 3 livelli:

**Livello 1 — Retrieval:** Trova ricette che condividono ≥2 ingredienti con l'input
**Livello 2 — Refinement:** Il LLM adatta quelle ricette, proponendo sostituzioni ragionevoli
**Livello 3 — Generazione guidata:** Se nessuna ricetta matcha abbastanza, il LLM genera un suggerimento nuovo CON DISCLAIMER:
> "Non è una ricetta classica, ma con questi ingredienti potresti provare una pasta con würstel e una crema di formaggio e noci."

**Livello 4 — Interazione umana:** Il sistema chiede all'utente: "Hai anche un uovo? Un po' di panna? Con quello potrei fare qualcosa di meglio."
Questo livello può essere implementato anche come suggerimenti automatici: "Se hai anche X, potresti fare Y."

### GNN (Graph Neural Networks) — Nota tecnica

Le GNN sono **un'applicazione di ricerca valida** per recommendation di ricette: gli ingredienti e le ricette formano naturalmente un grafo (ricetta → ingrediente → altra ricetta) e una GNN potrebbe scoprire sostituzioni non ovvie tra ingredienti.

**Perché NON le usiamo per questo progetto:**
- Questo è il **primo progetto software** di un Junior SWE. Ci sono già 3 tecnologie da imparare (React Native, Node.js, Python)
- La GNN aggiungerebbe un layer di complessità (preparazione dati, training, valutazione) che ritarderebbe di mesi il primo prototipo funzionante
- Il RAG semplice è comunque una **skill professionale** usata in produzione

**Futuro:** Dopo il MVP, quando l'app funziona e ci sono dati reali, si può valutare l'integrazione di una GNN come miglioramento del recommendation engine.

- **Comunicazione Node.js ↔ Python:** HTTP REST. Python espone endpoint POST /suggest via FastAPI

## Privacy & Dati

- I dati utente (preferenze, cronologia, piani) sono **crittografati in transito e a riposo**
- L'utente può **esportare e cancellare** tutti i propri dati in qualsiasi momento
- Gli ingredienti inseriti non vengono **mai usati per training** di modelli LLM
- Il Gemini API riceve solo le ricette retrieved + ingredienti correnti, nessun dato storico
- **Nota:** I modelli LLM non girano sul telefono dell'utente — la chiamata è sempre al backend/server, che a sua volta chiama API cloud (Gemini). L'embedding search (MiniLM) gira invece sul server Python. Questo è l'approccio standard per app mobile con AI

## Onboarding & Cold Start

- Al primo avvio, l'utente inserisce **3 ingredienti** che ha in casa (es. "uova, farina, latte") → riceve subito 3 ricette. Zero attesa, valore immediato
- Se l'utente non sa quali ingredienti inserire, suggerimenti: "Cosa hai nel frigo in questo momento?"
- Le preferenze alimentari sono raccolte **dopo** la prima generazione ricetta, non prima (non bloccare il valore)
- Dati campione: 5 ricette pre-caricate per demo anche senza ingredienti

## Failure Modes

| Scenario | Comportamento |
|---|---|
| **Nessuna ricetta nel DB matcha** | Livello 3 — il LLM genera un suggerimento nuovo con disclaimer: "Non è una ricetta classica, ma..." Poi Livello 4: suggerisci ingredienti extra ("Hai anche un uovo?") |
| **Match parziale (1-2 ingredienti)** | Il LLM adatta le ricette più vicine, propone sostituzioni. Es: "Non hai pomodoro? Puoi usare passata o pelati." |
| **LLM non disponibile (API down)** | Fallback: mostra le top-3 ricette dal retrieval puro, senza refinement. Meno belle ma funzionanti |
| **Errore di rete** | Cache locale delle ultime 20 ricette. Funzionalità limitate senza connessione |
| **Rate limit Gemini superato** | Coda richieste. Mostra messaggio: "Troppe richieste, riprova tra un minuto." Cache risultati comuni |
| **Ingresso ingredienti non validi** | Validazione lato client: avviso ma non bloccante. Lascia decidere all'utente |
